gridDim 太小，比如只有 36，每个 SM 只有一个 block、256 个线程，那时候每 SM 同时在路上的数据有多少？
我们设置的block是256，如果gridDim设置36，那就是一个sm，256线程，256*4b=1kb，远远不够；
若是gridDim设置216，每个sm里面就是6个block塞满了，就是1536个线程，1536*4b = 6kb；

v4b其实就是，每个线程每次次跳grid*block那么远，他实际的分组线程是是从blockIdx.0,threadidx.0到blockIdx.max,threadIdx.max;
我们block大小固定是256，然后就是增加grid的大小，但是要注意最大值，最大值是SM数量*max threads：36*1536；这里256是block，极大值也就是216;给所有SM塞满。

gridDim = 36 时每个 SM 只有一个 block，125.45 ÷ 36 ≈ 3.48 GB/s，这就是「一个 block 独自在一个 SM 上跑」的速度。

gridDim = 217：216 个 block 先跑完一波，每个负责 n/217 的数据，大约 0.647 ms。然后第 217 个 block 独自上场，它要搬 268.4 MB ÷ 217 ≈ 1.24 MB，按 3.48 GB/s 算要 0.355 ms。合计 1.002 ms——你实测 1.001 ms。

gridDim = 433：前两波约 0.648 ms，最后那个孤零零的 block 搬 0.62 MB，要 0.178 ms。合计 0.826 ms——实测 0.817 ms。

尾波的代价是「一个 block 的活」除以「单 block 的速度」，它正比于 1/gridDim。所以 grid 越大，非整倍数带来的损失越小；但太大又会退化回 v3 那样的会议开销。实践中的做法是取「SM 数 × 每 SM 常驻 block 数」的整倍数，你这张卡上就是 216 的倍数。
