### 3.2 预测一：vector add

- AI = 1 FLOP / 12 B ≈ 0.083
- 理论可达 = 0.083 × 448 = 37.3 GFLOP/s
- 实测 = 394.9 / 12 = 32.9 GFLOP/s
- 实测 ÷ 可达 = **88.1%**；实测 ÷ 峰值算力 = 0.14%（这个比值没有意义）

### 3.3 预测二：roofline_sweep（写于跑之前）

n = 2^26，每次调用 bytes = 8n = 512 MiB，FLOPs = 2K·n，AI = K/4
- 纯访存时间 t_mem = 0.537 GB / 394.9 GB/s ≈ **1.36 ms**（与 K 无关）
- 纯计算时间 t_comp = 2K·n / 23704 GFLOP/s ≈ **0.00566 × K ms**
- 预测耗时 = max(t_mem, t_comp)

| K | AI | 理论可达 (448) | 现实可达 (394.9) | 预测 median | 预测 GB/s | 瓶颈 |
|---|---|---|---|---|---|---|
| 4 | 1 | 448 | 395 | 1.36 ms | 395 | 带宽 |
| 8 | 2 | 896 | 790 | 1.36 ms | 395 | 带宽 |
| 16 | 4 | 1,792 | 1,580 | 1.36 ms | 395 | 带宽 |
| 32 | 8 | 3,584 | 3,159 | 1.36 ms | 395 | 带宽 |
| 64 | 16 | 7,168 | 6,318 | 1.36 ms | 395 | 带宽 |
| 128 | 32 | 14,336 | 12,637 | 1.36 ms | 395 | 带宽 |
| 256 | 64 | 23,704 | 23,704 | 1.45 ms | 370 | **拐点附近** |
| 512 | 128 | 23,704 | 23,704 | 2.90 ms | 185 | 算力 |
| 1024 | 256 | 23,704 | 23,704 | 5.80 ms | 93 | 算力 |
| 2048 | 512 | 23,704 | 23,704 | 11.6 ms | 46 | 算力 |

拐点位置：理论 K ≈ 4 × 52.9 ≈ 212，现实 K ≈ 4 × 60 = 240，都落在 128 和 256 之间。

### 3.4 我猜实测会在哪里偏离（跑完回来对答案）

1. K = 4 到 128 这一段，median 应该几乎不变，都在 1.36 ms 左右。
   K 增加 32 倍，耗时却不变，这就是 memory bound 的直接证据。
2. K = 256 偏离理论最多：t_mem（1.36）和 t_comp（1.45）几乎相等，
   访存和计算重叠不完美，猜实测只能到平台的 70–85%。
3. 平台低于 23.7 T，猜在 90% 左右。原因有两个：满载 FMA 会撞功耗墙降频，
   循环里的整数指令也会占掉 FP32 发射槽。
4. 如果低 K 段测出的 GB/s 超过 448，说明工作集落进了 L2
   （回去检查 n），不说明卡变快了。

### 3.5 Day 5 实测结论

| 项 | 值 | 备注 |
|---|---|---|
| FP32 平台（实测） | 24373 GFLOP/s | 标称 24256 的 100.5%，无降频 |
| DRAM 带宽（1读1写） | 385.3 GB/s | 理论 86.0%；vector add 2读1写测 394.9 |
| 经验平衡点 | 24373 / 385 = 63.3 FLOP/B | 理论 54.1 |
| 曲线开始偏离屋顶 | AI ≈ 48 | 比两个 ridge 值都更早 |
| 圆角区间 | AI 48 ~ 256 | 最差点 AI=64，超出 max 模型 37.6% |
| ILP 影响 | K=512 无差异；K=2048 慢 11% | 混淆变量未排除，待 unroll 对齐重测 |

结论：
1. 32 倍计算量增长而耗时不变（K=4→128）= memory bound 的判定标准。
2. 真实重叠介于 max(t_mem,t_comp) 与 t_mem+t_comp 之间，尖角变圆。
3. 满 occupancy 下 TLP 足以掩盖 FFMA 延迟，ILP 只在无余量时显现。
4. 「卡的带宽」随读写比变化，不是单一常数。

nvidia-smi 实测满载稳态 2857–2880 MHz（取 2.87 GHz）。
未撞功耗墙（160/180 W），未撞温度墙（64°C）。

### 3.7 ILP 结论（对照实验，unroll 已对齐）

K=2048：单链 11.244 ms vs 四链 11.278 ms → 无差异
上一轮观察到的 11% 差距源于 unroll 不一致导致的循环开销，非 ILP。
结论：满 occupancy（48 warp/SM，12 warp/调度器）下 TLP 足以掩盖 FFMA 延迟。
待 W3 用 __launch_bounds__ 压低 occupancy 后复测，届时 ILP 应显现。

方法论教训：对照实验必须只改一个变量。第一版把 ILP 和循环开销混在一起，
差点得出错误结论。

### 3.9 ncu

ncu = 打开 GPU 硬件计数器，测「为什么」；benchmark 测「多快」。
ncu 报的时间不可信（profiling 开销 + 每个指标要重跑一遍 kernel）。

坑 1：-c N 是「匹配到的前 N 次 launch」，不是「每个 kernel N 次」。
      我的程序第一个 launch 是自检的 <64>，所以 -c 3 只抓到 <64> 和 <4>。
坑 2：指定模板特化要用 mangled 名 + --kernel-name-base mangled。
      查名字：cuobjdump -symbols <exe> | grep <kernel>
坑 3：--clock-control none，否则 ncu 锁 base clock，吞吐对不上。
坑 4：指标名各版本不同。本机是 dram__bytes_op_read（不是 dram__bytes_read）。

#### 指令验证结果（✓ 全部吻合）
| K | FFMA | /n | FADD | FMUL |
|---|---|---|---|---|
| 4  | 268,435,456   | 4.00  | 6n | 0 |
| 64 | 4,294,967,296 | 64.00 | 6n | 0 |

结论：kernel 未被优化掉；fmaf 全部融合（FMUL=0）；
      FADD=6n 与 K 无关 = 四链版的 3 次初始化 + 3 次求和。

真实 FLOPs = 2·FFMA + FADD = (2K+6)n，代码传的 2Kn 在 K=4 时低估 75%，
K=2048 时仅低估 0.15%。低 AI 区的 GFLOP/s 不是关注对象，故不影响结论。
教训：手算 FLOPs 在低 AI 区有系统性偏差，边角运算占比不可忽略。

#### DRAM 流量验证（K=4，n=2^26）

注意：ncu 的 Mbyte = 10^6 B，不是 MiB。

| 项 | 假设 | 实测 | 偏差 |
|---|---|---|---|
| read  | 268.44 MB | 268.88 / 269.17 | +0.2% |
| write | 268.44 MB | 250.42 / 247.58 | −7.3% |
| total | 536.87 MB | 519.30 / 516.75 | −3.5% |

结论：
1. bytes = 8n 成立 → 前四步的 GB/s 与 roofline 图全部有效。
2. 无 write-allocate（读写量均未翻倍）→ 写完整覆盖 sector，合并访问到位。
3. 写少 18 MB 的原因：L2 是 write-back，kernel 结束时脏数据未全部刷回，
   落在 ncu 采样窗口外。18 MB < 32 MB L2，物理上讲得通。
4. 读不受影响：读必须同步完成，写可以滞后。

坑 5：ncu 挂进程会污染 benchmark 的 median（本次 K=2048 从 11.28 涨到 12.15，
      但 min 不变）。profiling 和 benchmarking 分开跑。

方法论：验证看数量级吻合，不追小数点。7% 是采样边界，500% 才是假设错了。
