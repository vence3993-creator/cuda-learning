> 本周第一次"理论被实测打脸"的一天。结论不是背来的，是六组实验 + ncu 逼出来的。

## 2. 实验设计

三个 kernel，**搬运字节数完全相同**，唯一差别是 global memory 的地址模式：

```cuda
copyKernel              out[y*n+x] = in[y*n+x];   // 读写都连续，性能上界
transposeReadCoalesced  out[x*n+y] = in[y*n+x];   // 读连续、【写跨行】
transposeWriteCoalesced out[y*n+x] = in[x*n+y];   // 【读跨行】、写连续
```

> ⚠️ 命名坑：`rd_coal` = read coalesced = **写跨行**；`wr_coal` = write coalesced = **读跨行**。
> 下文一律用"写跨行 / 读跨行"，避免每次都要在脑子里翻译。

控制变量：不写 `__restrict__`（会让编译器走 LDG.NC 只读缓存路径，污染 l1tex 指标）；
`-O3 -lineinfo`；benchmark 用 cudaEvent，warmup 10 + 200 次取中位数。

---

## 3. 转置的死结

矩阵行主序存储，`A[y][x]` 实际是 `A[y*N + x]`。转置定义：

```
out[x*N + y] = in[y*N + x]
```

warp 内 `threadIdx.x` 变化 → **x 在变，y 不变**：

| | 索引 | x 变化时地址步长 | 结果 |
|---|---|---|---|
| 读 `in[y*N+x]` | x 在**低**位 | 4 B | 连续 |
| 写 `out[x*N+y]` | x 在**高**位 | N×4 = **16 KB** | 跨行 |

**同一个变量 x，在读式里处于低位，在写式里必然处于高位。**
把索引反过来写只是把惩罚从写端挪到读端，总量不变。naive 版无法绕开。

| block | 线程/block | copy | 写跨行 | 读跨行 |
|---|---|---|---|---|
| (32,32) | 1024 | 327.2 · 73%峰 | 168.8 (51.6%) | 269.2 (82.3%) |
| (32,8) | 256 | 385.1 · 86%峰 | 280.3 (72.8%) | 187.0 (48.6%) |
| (16,16) | 256 | 382.4 · 85%峰 | **374.8 (98.0%)** | 296.0 (77.4%) |
| (8,8) | 64 | 385.8 · 86%峰 | **375.8 (97.4%)** | 187.9 (48.7%) |
| (64,4) | 256 | 386.9 · 86%峰 | 285.8 (73.9%) | 186.8 (48.3%) |
| (128,2) | 256 | 385.8 · 86%峰 | 290.8 (75.4%) | 187.8 (48.7%) |

**同一个算法、同样的 128 MB 流量，只换 launch 几何，375 vs 169，差 2.2 倍。**

### 4.2 confounder：(32,32) 那组整体偏慢

它的 **copy baseline 就已经慢了 15%**（327 vs 385），不是转置的问题。
1024 线程/block，而每 SM 上限 1536 → 只能驻留 **1 个 block**，occupancy 66.7%。
其余组 256/64 线程可塞满 1536 → 100%。访存密集 kernel 靠 warp 数量掩盖 DRAM 延迟。

**跨组比绝对 GB/s 无效，只能比组内相对百分比。**

### 4.3 ncu 指标（block = 32×8）

| kernel | ld sect/req | st sect/req | DRAM read | DRAM write | DRAM %peak | 实测 GB/s |
|---|---|---|---|---|---|---|
| copy | **4** | **4** | 67.4 MB | 62.8 MB | **89.2%** | 385 |
| 写跨行 | 4 | **32** | 68.0 MB | 67.1 MB | **55.0%** | 280 |
| 读跨行 | **32** | 4 | 67.4 MB | 53.7 MB | **40.4%** | 187 |

补测 block = (8,8) 读跨行：`ld sect/req = **8**`。

> 读跨行的 DRAM write 只有 53.7 MB（低于理论 64 MB）：不是丢数据，是 kernel 结束时
> 还有约 10 MB 脏数据留在 L2 未刷回。profile 模式只跑一次 launch，这个尾巴很明显。

## 5. 核心机理：一个 warp 会碰到几个 sector

**不变量：一个 warp 永远只需要 32 × 4 = 128 B 有用数据。** 变的是它摊在几个 sector 上。

读跨行 `in[x*n+y]`，x 每变 1 地址跳 `n×4 = 16 KB` —— 远大于 32 B，
**不同的 x 必然落进不同 sector，永远合并不了**。

warp 是 32 个连续 tid，而 `tid = tz·bx·by + ty·bx + tx`（x 变化最快），所以：

```
sectors/req = min(32, bx)          ← 只跟 blockDim.x 有关
每 sector 用掉 = 128 / sectors = 4·(32/bx) 字节
```

### 逐地址验证（blockIdx=(0,0), n=4096, 地址 = (x*4096+y)*4 字节）

**(32,8)**：tid = ty×32 + tx → warp 0 = ty 0, tx 0–31。x 取 32 个值，y 只有 1 个：

```
x=0  → 字节      0   sector [0, 32)        用 [0,4)      = 4 B
x=1  → 字节  16384   sector [16384,16416)  用 4 B
...
x=31 → 字节 507904
→ 32 个 sector，每个用 4/32
```

**(8,8)**：tid = ty×8 + tx → warp 0 = ty 0–3, tx 0–7。x 取 8 个值，y 有 4 个连续：

```
x=0, y=0..3 → 字节 0,4,8,12   sector [0,32)  用 [0,16)  = 16 B
...
x=7, y=0..3
→ 8 个 sector，每个用 16/32
```

| block | warp 形状 | sectors/req | 利用率 | ncu 实测 |
|---|---|---|---|---|
| (32,8) | 32 行 × 1 | 32 | 12.5% | **32** ✅ |
| (16,16) | 16 行 × 2 | 16 | 25% | — |
| (8,8) | 8 行 × 4 | 8 | 50% | **8** ✅ |
| (64,4) / (128,2) | 32 行 × 1 | 32 | 12.5% | — |

**`bx ≥ 32` 后 warp 形状锁死** —— (32,8)/(64,4)/(128,2) 完全等价。
这解释了它们读跨行带宽一致到小数点后一位：187.0 / 186.8 / 187.8。

## 6. 为什么"浪费"没有真的发生

每个 warp 没用掉的部分，被**同 block 的兄弟 warp**拿走了：

| block | 填满一个 sector 需要 | block 里有 |
|---|---|---|
| (32,8) | 8 个 warp (ty 0–7) | 8 ✅ |
| (16,16) | 4 个 warp | 8 ✅ |
| (8,8) | 2 个 warp (ty 0–3 / 4–7) | 2 ✅ |

一个 sector = 32 B = 8 个 y 值，block 覆盖 `by` 个 y。**只要 `by ≥ 8`，block 必然覆盖完整 sector。**
(128,2) / (64,4) 的 by < 8，靠相邻 block 在 L2 里合并 —— 实测也成功了（DRAM 仍是 67 MB）。

两侧机制不同：
- **写侧**：store 绕过 L1 直接进 L2，多 warp 碎片在 L2 合并成整 sector 再刷 DRAM → **补全后发出**
- **读侧**：DRAM 一次送来完整 32 B，第一个 warp 用掉自己那份，**余下留在 L1**，兄弟 warp 随后命中 → **取一次、复用**

> 合并的单位是 **block**，不是 cache 容量。(32,8) 读跨行时一个 block 的读侧足迹只有
> 32 行 × 32 B = **1 KB**，几微秒内跑完。32 MB L2 在这里是杀鸡用牛刀，
> 换 2 MB 的 L2 结果一样。**"大 L2 救了场"这个说法是错的。**

### 💡 本日最重要的一句

```
sectors/request  →  单条指令的地址发散度   (warp 层, L1TEX)
dram__bytes_*    →  最终真的搬了多少字节   (DRAM 层, block 合并之后)
```

**两者可以完全脱钩。** 实测：sect/req 报告 32（理论 8 倍浪费），
而三个 kernel 的 DRAM 流量全是 **67 MB，零放大**。

## 7. 被数据打死的三个假设

| # | 假设 | 证伪依据 |
|---|---|---|
| 1 | naive transpose 浪费 8 倍显存带宽 | 三个 kernel 的 `dram__bytes_op_*` 都是 67 MB，放大倍数 ≈ 1.0 |
| 2 | 段长 ≥ 32 B 才不浪费，by 越小越差 | by=2 (75.4%) > by=4 (73.9%) > by=8 (72.8%)，**反而单调变好** |
| 3 | L1TEX sector 发射端是瓶颈 | (8,8) 的 sect/req 只有 8，是 (32,8) 的 1/4，性能却完全相同（187.9 vs 187.0） |

另外两处**我自己的预判也错了**：
- 预判 (16,16) "warp 横跨两行 → 更碎"。实际它是全场最好的（写跨行 98%）。
  warp 覆盖 2 行 × 16 float = 2 × 64 B = 4 个 sector，和 32 宽连续完全相同。
  **横跨多行只在"每行连续段 < 32 B"时才有害。**
- 预判 "写跨行比读跨行更疼"。六组数据全部相反，**读跨行始终更慢**。
  写侧合并在 L2 里几乎免费，剩下的是本质不对称：
  **读在关键路径上，warp 必须 stall 等数据；写是 fire-and-forget。**

## 8. ⚠️ 待查：性能差距的真正来源

**已排除**：字节浪费（DRAM 流量相同）、DRAM 带宽饱和（越慢越闲）、sectors/request（8 和 32 一样慢）。

**唯一存活的经验规律** —— 读跨行性能只跟 `by` 相关，跟 bx / sect/req / 线程数都无关：

| by | block 每行连续字节 | 读跨行 %copy |
|---|---|---|
| 2 | 8 B | 48.7% |
| 4 | 16 B | 48.3% |
| 8 | 32 B | 48.6% / 48.7% |
| 16 | 64 B | **77.4%** |
| 32 | 128 B | **82.3%** |

两个可疑之处：
1. `by ≤ 8` 的四组 —— 四个完全不同的 block 形状，带宽是 **187.8 / 186.8 / 187.0 / 187.9**，
   一致到小数点后一位。这种精度不是巧合，是撞到了同一堵墙。
2. 这堵墙大约是 copy 的一半（385/2 = 192.5 vs 实测 187）。干净的 2 倍关系通常意味着
   某个硬件粒度被浪费了一半 —— 比如"最小访问单位是 **64 B**"而请求只有 32 B。
   注意拐点出现在 by=16（**64 B**）而非 32 B，和这个猜想吻合。

**下一步验证**：对比 (8,8) 和 (16,16) 读跨行的 `dram__bytes_op_read.sum`
- 两组都 ≈67 MB → 瓶颈在访问**次数**（DRAM bank 激活、行缓冲），不在字节数
- (8,8) ≈128 MB → GDDR7 的有效访问粒度是 64 B，今天"sector=32 B 是最小传输单位"需修正

**不影响 W2，留作遗留问题。**

## 9. 与 Day 5 Roofline 的冲突

转置的算术强度 = **0 FLOP/B**，位于 Roofline 最左端，理应死死贴在斜线上（带宽饱和）。

但实测：**越慢的 kernel，DRAM 利用率反而越低**（89% → 55% → 40%）。
显存总线在等、在闲、吃不饱。

**Roofline 假设瓶颈是 DRAM 字节数，而这里被一个它完全没建模的资源卡住了。**
Roofline 给的是上界，不是诊断工具。W2 会反复撞到这件事。

## 10. W2 的验收标准（shared memory 版本）

不是"变快了多少"，而是四项同时满足：

```
st sectors/request :  32    → 4        必须达成
ld sectors/request :   4    → 4        必须保持
dram__bytes_op_*   :  67 MB → 67 MB    必须不变（本来就没浪费，不该变）
dram %peak         :  55%   → 85%+     结果指标
```

- 快了但 sect/req 还是 32 → 改的是别的东西，运气好
- sect/req 降到 4 但 DRAM 字节涨了 → shared tile 写回时引入了新的跨行
- 四项全中 → 优化生效且机理正确

## 附：CUDA 层级速查

```cuda
kernel<<<gridDim, blockDim>>>(args);   // 第一个是 grid，第二个是 block
```

`dim3(x, y, z)`，未指定维度自动填 1。全局坐标通式，每个维度一样：

```cuda
坐标 = blockIdx * blockDim + threadIdx
```

**block 内线程按混合进制压成一维**（每位基数 = 对应的 blockDim，不是 10）：

```
tid = threadIdx.z * (blockDim.x * blockDim.y)
    + threadIdx.y *  blockDim.x
    + threadIdx.x                              ← x 变化最快
```

每 32 个连续 tid = 一个 warp。**所以 warp 形状只由 blockDim 决定，与 grid 无关。**

展平二维索引必须写 `y*w + x`（x 在低位），写成 `x*h + y` 会让相邻线程地址差 `h*4` 字节，
直接毁掉 coalescing —— 这就是本日两个 transpose 变体的全部差别。

硬件上限（对照 Day 1 deviceQuery）：block 最大 1024 线程，blockDim.z ≤ 64，
gridDim.y/.z ≤ 65535。超限 launch 静默失败，必须 `cudaGetLastError()` 检查。

## 一句话验收

> copy 跑到 385 GB/s、DRAM 利用率 89%。naive transpose 只有 187–280 GB/s。
> 原因**不是**浪费显存带宽 —— 三个 kernel 的 DRAM 流量都是 67 MB，完全相同，
> per-warp 的碎片被同 block 的兄弟 warp 补齐了。
> `sectors/request` 报告的 32 是**请求层面**的发散度，和**字节层面**的浪费完全脱钩。
> 真正的瓶颈尚未定位：DRAM 利用率反而从 89% 掉到 40%，说明显存总线在闲着，
> 卡住的是别的东西。**已排除三个候选解释，待 W2 回头再查。**
