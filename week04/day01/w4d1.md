## 1. 原理

### 1.1 LayerNorm 在做什么

输入 `[M, N]`，每一行（一个 token，N = hidden size）**各自独立**归一化：

```
μ  = Σ xᵢ / N
σ² = Σ (xᵢ − μ)² / N            ← 除以 N（有偏），和 PyTorch 一致
yᵢ = (xᵢ − μ) · rsqrt(σ² + ε) · γᵢ + βᵢ        ε = 1e-5
```

- γ、β 长度为 N，所有行共用
- ε 的作用：整行相同时 σ² = 0，防止除以 0
- 骨架和 softmax 一样：**行内归约 → 用归约结果处理每个元素**
  - softmax 归约 max、sum；LayerNorm 归约 Σx、Σ(x−μ)²
  - 必须是 **All**Reduce：32 个 lane 都要拿到 μ、σ²（`warpReduceSum` 是 xor 蝶形，天然 all-reduce）

### 1.2 求方差的三种方法

| 方法 | 做法 | 特点 |
|---|---|---|
| 两遍 | 先求 μ，再求 Σ(x−μ)² | 数值稳定；第二遍依赖第一遍 |
| 单遍 | 同时累加 Σx、Σx²，σ² = E[x²] − μ² | 只扫一遍；**大数相减，数值不稳定** |
| Welford | 增量更新 (n, μ, M2)，两段结果可合并 | 稳定 + 单遍；D2 展开 |

### 1.3 单遍公式为什么会崩：灾难性抵消（catastrophic cancellation）

偏移组 `x = 1000 + u`，`u ∈ [-1, 1)`：

```
E[x²] = 10⁶ + 2000·E[u] + E[u²] ≈ 1,000,000.333
μ²    ≈ 1,000,000.000
真实方差 ≈ 0.333   ← 要从两个 ~10⁶ 的数相减得到
```

float32 尾数 24 位（≈ 7 位十进制有效数字），**数越大，相邻两数的间隔越粗**：

| 数值范围 | 相邻 float 间隔 | 出现在哪 |
|---|---|---|
| [2⁹, 2¹⁰) ≈ 1000 | 2⁻¹⁴ ≈ 6.1e-5 | x 本身、μ |
| [2¹⁹, 2²⁰) ≈ 10⁶ | 2⁻⁴ = 0.0625 | E[x²]、μ²（偏移 1000） |
| [2²⁶, 2²⁷) ≈ 10⁸ | 2³ = 8 | E[x²]、μ²（偏移 1e4） |
| [2²⁹, 2³⁰) ≈ 10⁹ | 2⁶ = 64 | Σx² 累加中间值（偏移 1000） |

- 两个接近的大数相减本身是精确的，但相减**之前**两者都只能落在刻度上 → **算出的方差只能是刻度间隔的整数倍**
- 两遍法先减 μ：(x−μ) ∈ [-1, 1)，平方 < 1，没有大数相减
- 比喻：用精度 10 kg 的地磅，称"卡车 + 一张纸"减"卡车"来求纸的重量

### 1.4 关键观察：寄存器上的"两遍"不多花 DRAM 带宽

一 warp 一行，N = 1024：每个 lane 缓存 32 个 float（`float buf[32]`），第 k 次读 `x[k*32 + lane]` → 32 个 lane 读连续 128 B，合并访问。

```
DRAM ──读一次──▶ 寄存器 buf
                  第 1 遍：Σbuf        → all-reduce → μ
                  第 2 遍：Σ(buf−μ)²   → all-reduce → σ²
                  第 3 遍：归一化
寄存器 ──写一次──▶ DRAM
```

- 和单遍法相比：DRAM 流量**完全相同**（读一次、写一次）
- 和"从 DRAM 读两遍的两遍法"相比：省掉一次 64 MB 读
- 多付出的代价：一轮**串行**的 all-reduce（5 次 shuffle）+ 每 lane ~32 次乘加
- 和 W3 online softmax 在 N = 1024 时没收益是同一个道理：数据本来就在寄存器里
- 单遍 / Welford 的价值在**一行放不进寄存器**时才体现（→ D2）

### 1.5 Roofline

```
每元素：读 4 B + 写 4 B = 8 B（γ、β 只有 N 个，常驻缓存，忽略）
       约 8 FLOP（累加、减 μ、平方累加、乘 rstd、乘 γ、加 β）
AI ≈ 1 FLOP/B  ≪  拐点 54 FLOP/B  → 纯 memory bound
理论下限 = 128 MB ÷ 448 GB/s ≈ 0.30 ms（和 softmax 一样）
```

memory bound → 多做几条计算指令几乎免费，**前提是有足够多的访存请求在途来填满延迟**（见 4.3）。

## 2. 实现

### 2.1 框架（从 W3 D4 softmax 框架改来）

- 三组输入：常规 `U[-1,1)`、偏移 `1000 + U[-1,1)`、偏移 `1e4 + U[-1,1)`
  - **在 float 里生成**，CPU 参考和 GPU 吃同一份数据
- γ ∈ [0.5, 1.5)、β ∈ [-0.5, 0.5)（自定范围，只要求输出量级 ~1）
- CPU 参考：double 两遍法
- 参考体检：γ = 1、β = 0 时输出每行均值 ≈ 0、方差 ≈ 1（三组都 OK）
- checker：最大绝对误差 < 1e-4；**NaN / inf 单独计数**（`fmax` 会吞掉 NaN，`NaN > x` 恒为 false）；只报告不中止
- 输出先 `cudaMemset(0xFF)` 毒化成 NaN：kernel 漏写任何位置都能查出来
- `N` 通过 `-DNCOLS` 从 Makefile 传入，不同 N 编成不同文件名

### 2.2 三个版本

**通用骨架**

```cuda
constexpr int VPT = NCOL / WARP_SIZE;                          // 必须 constexpr
int row  = (blockIdx.x * blockDim.x + threadIdx.x) / WARP_SIZE; // 必须带 blockIdx
int lane = threadIdx.x % WARP_SIZE;
if (row >= m) return;      // 同一 warp 的 row 相同 → 整个 warp 一起退出，不影响 shuffle
```

- **v0 单遍**：一个循环里同时 `s1 += v; s2 += v*v`；`var = s2/N − μ²`。**故意不加 `fmaxf(var, 0)`**——对照组的任务是把问题暴露出来
- **v1 两遍（寄存器）**：第 2 遍 `buf[i] -= mu; s2 += buf[i]*buf[i];`，第 3 遍直接 `buf[i] * rstd * γ + β`
- **v2 float4**：`V4 = NCOL / 128`，第 i 次访问 float4 下标 `k = i*32 + lane`
  - i = 0：lane0 → float 0~3，lane1 → 4~7，…，lane31 → 124~127；warp 一次读连续 512 B
  - **γ、β 用同一个 k 按 float4 读**：行起点是 NCOL 的整数倍，行内第 k 个 float4 = 第 4k~4k+3 列，与 γ、β 天然对齐
  - 前提：地址 16 B 对齐。`cudaMalloc` ≥ 256 B 对齐、行偏移是 512 B 的倍数 → 安全；N 不是 4 的倍数会直接 `misaligned address` 崩溃 → `static_assert(NCOL % 128 == 0)`
  - 加法顺序和 v1 不同（(x+y)+(z+w)），最后几位误差不同，正常

### 2.3 `#pragma unroll` 为什么不能省

寄存器**没有地址**，不能用运行时下标访问。循环完全展开后 `buf[0]…buf[31]` 在编译期变成具体寄存器名；不展开则整个 buf 被放进 local memory（物理上在 DRAM）。

`buf[i]` 在源码里多写几次不会多读——它就是寄存器。`buf[i]*buf[i]` 和先拷到临时变量 `d*d` 编译出来一样（`FADD` + `FFMA`）。

## 3. 结果（N = 1024，M = 16384，benchmark 中位数）

| Kernel | Duration | GB/s | 占 D2D | 偏移 1000 max_abs | 偏移 1e4 |
|---|---|---|---|---|---|
| D2D copy | 0.3489 ms | 384.7 | 100% | – | – |
| v0 单遍 | 0.3500 ms | 383.4 | 99.7% | **3.30** | max_abs 489，**5491 行 NaN（33.5%）** |
| v1 两遍（寄存器） | 0.3510 ms | 382.4 | 99.4% | 3.06e-4 | 4.00e-3 |
| v2 float4 | 0.3485 ms | 385.1 | 100.1% | 2.62e-4 | – |

常规组三个版本 max_abs 都是 4.77e-07，PASS。

### 3.1 偏移组 v0：用"刻度"模型解释每个数字

- **偏移 1000**：方差只能是 0.0625 的整数倍；真实值 0.333 ≈ 5.3 格，要误差超过 5 格才会变负 → **没有 NaN**
  - max_abs = 3.30：最差的行方差掉到约 1 格（0.0625），rstd 从 1.73 变成 4（差 2.27），× |x−μ| ≤ 1 × γ ≤ 1.5 → 上限约 3.4 ✓
- **偏移 1e4**：刻度间隔是 8，真实方差 0.333 不到 1/24 格 → 算出来基本只有 0、−8、+8
  - 方差 = 0 → rstd = 1/√ε ≈ 316 → × 1.5 ≈ 474，对上 max_abs 489 ✓
  - 方差 < 0 → `rsqrtf(负数)` = NaN
  - NaN 数 5,622,784 = **5491 × 1024**：方差按行算，所以**整行整行地 NaN**
- 以上是从数字反推的结论；想验证可让 lane 0 打印前几行的 var（可选）

### 3.2 偏移组 v1 / v2 也 FAIL：不是 bug，是阈值对偏移组太严

- v1 误差比 v0 小 **一万倍**（3e-4 vs 3.3），两遍法救了方差
- 剩余误差来自 **μ 本身**：1000 附近的 float 间隔 ≈ 6.1e-5，μ 哪怕只差一次舍入也有 ~3e-5 误差，× rstd × γ（最大 ~2.6）→ 输出端接近 1e-4。实测 3e-4 ≈ μ 偏差两个刻度，**接近 float32 的极限**
- 偏移 1e4 间隔再粗 16 倍 → 4e-3，比例一致
- 偏移组是对照实验，只记录 max_abs 和 nan/inf，不套常规组的 PASS 标准
- D2 可用的技巧：每行先减一个参考值再累加，压掉 μ 的误差

### 4.1 三项验证

1. **DRAM 读一次** ✓：ncu 的 MB 是 10⁶ 字节，64 MiB = 67.1 MB，读取量正好是 x 读一遍。γ、β（共 8 KB）基本命中缓存
2. **0 spill** ✓：local memory load = 0，buf 全在寄存器里
3. **load 指令数正好少 4 倍** ✓：
   - v0 / v1：16384 行 × 96 次（x 32 + γ 32 + β 32）
   - v2：16384 行 × 24 次（x 8 + γ 8 + β 8）

### 4.2 谜题：为什么 DRAM 写只有 48~54 MB，不是 67 MB？

- L2 是**写回式**缓存：kernel 写出的数据先落在 L2，缓存行被换出时才写进 DRAM
- kernel 结束时最后十几 MB 还在 L2（32 MB 装得下），写回发生在 kernel 之后，不算进这次的 DRAM 统计
- 证据：`lts__t_bytes ≈ 135 MB` = 读 67 + 写 67，**L2 看到了全部读写**
- 推论：ncu 单次时长（~310 µs）比 benchmark 中位数（~350 µs）短——benchmark 连续发射，每次都要替上一次补完写回
- 用实际 DRAM 字节数 / 时长：v0 ≈ 374 GB/s，v1 ≈ 375 GB/s，v2 ≈ 384 GB/s，和 D2D 对得上
- **README 的 Duration 用 benchmark 中位数，不用 ncu 单次时长**

### 4.3 Occupancy 与在途字节数

按 sm_120 每 SM 64K 寄存器、最多 48 warp、每 block 4 warp 估算（可用 `ncu --section Occupancy` 核对）：

```
48 寄存器 → 每 warp 1536 个 → 42 warp → 按 block 取整 40 warp → 理论 83%   实测 78%
59 寄存器 → 取整到 64 → 每 warp 2048 个 → 32 warp → 理论 67%              实测 61%
```

v2 的活跃 warp 少了约五分之一，带宽却没掉：

```
在途字节数 ≈ 活跃 warp 数 × 每 warp 同时发出的 load 数 × 每次 load 的字节数
```

v2 每次 load 搬 16 B（4 倍），在途总字节反而更多。→ **"occupancy 越高越好吗？"的标准反例**

### 4.4 修正：v0 vs v1 的真正区别

v0 其实也做了**两次** all-reduce（Σx 和 Σx²）。区别是：**v0 的两次归约互不依赖，可以交错执行；v1 的第二次必须等第一次做完（串行依赖）**。memory bound 下这段等待被其他 warp 的访存填满，所以两者速度几乎一样。

## 5. spill 实验

| N | 每 lane 缓存 float 数 | v0 / v1 / v2 寄存器 | spill store / load（字节） | 理论 occupancy（估算） |
|---|---|---|---|---|
| 1024 | 32 | 48 / 48 / 59 | 0 | 83% / 83% / 67% |
| 4096 | 128 | 149 / 167 / 158 | **0** | **约 25%** |
| 8192 | 256 | 255 / 255 / 255 | 92·140 / 140·188 / 212·212 | **约 17%** |

- **8192 必然 spill**：buf 就要 256 个，而每线程最多 255 个寄存器，这是硬上限
- **4096 不 spill 但 occupancy 塌到 1/4**——事先担心这是"内伤"，实测**完全没掉**（见下）
- v2 在 8192 溢出最多：float4 要占 4 个连续寄存器，第 3 遍还要额外装 γ、β 的 float4（推测，分配由编译器决定）
- spill 只溢出**超出的部分**：v0 store 92 B = 23 个 float，不是整个 buf

带宽实测（`make run N=…`，常规组，benchmark 中位数；M = 2²⁴ / N，总流量不变）：

| N | v0 | v1 | v2 |
|---|---|---|---|
| 1024 | 0.3500 ms · 383.4 GB/s · 99.7% | 0.3510 ms · 382.4 GB/s · 99.4% | 0.3485 ms · 385.1 GB/s · 100.1% |
| 4096 | 0.3491 ms · 384.4 GB/s · 99.6% | 0.3490 ms · 384.6 GB/s · 99.7% | 0.3441 ms · 390.1 GB/s · 101.1% |
| 8192 | 0.3695 ms · 363.3 GB/s · **94.4%** | 0.3715 ms · 361.3 GB/s · **93.9%** | 0.3457 ms · 388.3 GB/s · **100.9%** |

### 5.1 N = 4096：occupancy 只剩 1/4，带宽却一点没掉

- 每个 warp 循环展开后**一口气发出很多个互不依赖的 load**（v1：x 就有 128 次，每次 warp 读 128 B）
- 在途字节数 ≈ 每 SM 12 warp × 36 SM × 每 warp 128 次 × 128 B ≈ 7 MB
- 喂满带宽需要的在途字节（Little 定律）≈ 带宽 × 延迟 ≈ 448 GB/s × 几百 ns ≈ 几百 KB
- 远远够用 → **warp 少，但每个 warp 在途的请求多（ILP），把 occupancy 的损失补回来了**
- 教训：低 occupancy ≠ 低带宽；判断标准是在途字节数，不是 occupancy 百分比
- 修正：事先"内伤"的判断是错的，以实测为准

### 5.2 N = 8192：spill 最多的 v2 反而最快

- v0 / v1 掉到 ~94%，v2 仍是 ~101%
- spill 的静态字节数只有一两百 B，相对每行 32 KB 很小，且多半命中 L1 → **spill 本身未必是主因**
- 推测（未验证）：每 SM 只剩 ~8 个 warp，v0 / v1 每行要发 ~1024 条访存指令（x、γ、β 各 256 次读 + 256 次写），v2 只要 ~256 条；warp 很少时，指令发射 / LSU 吞吐可能先成了瓶颈，float4 把这部分压力降到 1/4
- D2 开场验证：`ncu --section WarpStateStats --section MemoryWorkloadAnalysis`（N = 8192，v1 vs v2），看主要 stall 原因
- 教训：**"spill → 变慢"是经验法则，不是定律；要实测，再用 ncu 找原因**

## 6. 寄存器与 spill 原理

### 6.1 存储层次（延迟为量级）

| 位置 | 访问延迟 | 容量 | 谁能用 |
|---|---|---|---|
| 寄存器 | ~0，指令直接读写 | 每 SM 64K × 4 B = 256 KB | 单线程私有 |
| L1 / shared | 几十周期 | 每 SM ~100+ KB | block / SM |
| L2 | ~两百周期 | 32 MB | 全部 SM |
| DRAM | 几百周期 | 8 GB | 全部 SM |

算术指令的操作数**只能是寄存器**（或立即数）：`FFMA R3, R1, R2, R3` = R1 × R2 + R3 → R3。

### 6.2 分配规则

1. **编译时定死**：ptxas（PTX → SASS 的汇编器）分配，运行时不变
2. **同一 kernel 所有线程一样多**，按整个 kernel 里最紧张的时刻分配
3. **每线程最多 255 个**：SASS 寄存器编号 8 位 = 256 个，其中 RZ 是恒零寄存器，可用 R0~R254

### 6.3 需要多少寄存器 = 同时活着的值有多少

**活跃区间（live range）**：一个值从被算出到最后一次被使用，期间一直占一个寄存器。

v1 的 buf 从第 1 遍读入一直活到第 3 遍写出 → 整个 kernel 期间都占着 VPT 个寄存器，再加杂项（64 位指针每个 2 个寄存器、lane、μ、rstd、临时变量、γ/β 读入值）：

```
N = 1024：32  + ~16    = 48
N = 4096：128 + ~20~40 = 149~167
N = 8192：256 + …      > 255 → 放不下
```

### 6.4 spill

- 某一时刻要活着的值 > 可用寄存器 → 编译器把暂时用不到的值**先存出去、用时再取回**
- 存到 **local memory**：线程私有地址空间，**物理上在 DRAM**，经 L1 / L2 缓存
  - "local" 指作用范围（线程私有），不是物理位置近
  - 少量 spill 可能大多命中 L1，不一定付全额代价，但仍远慢于寄存器，且占 L1 / L2 带宽
- SASS 指令：`STL`（存）/ `LDL`（取）
- `-Xptxas -v` 输出：
  - `stack frame`：每线程在 local memory 预留的字节数
  - `spill stores / loads`：代码里 STL / LDL 的**静态**字节数，不是运行时流量（在循环里可能执行多次）

### 6.5 寄存器 vs occupancy 的交换

```
每 SM 可驻留 warp ≈ 65536 ÷ (每线程寄存器数 × 32)，上限 48（实际再按分配粒度和 block 取整）
48 寄存器 → ~42 warp；160 → ~12 warp；255 → ~8 warp
```

寄存器多 → 驻留 warp 少 → 同一时刻在途的访存请求**可能**变少 → DRAM 延迟填不满 → 带宽喂不饱。
（注意：总指令数**不变**，变少的是同时在途的请求。）

但 warp 少不等于在途请求少：每个 warp 发出的独立 load 越多（ILP），越能补回来。N = 4096 实测 occupancy 25% 仍满带宽（见 5.1）。

控制手段：`__launch_bounds__`、`-maxrregcount` —— 用 spill 换 occupancy，哪边划算只能实测。

### 6.6 根治思路（→ D2）

1. **更多线程分担一行**：一个 block 一行，4 个 warp 共同缓存，N = 8192 时每线程只要 64 个 float（v3）
2. **不缓存**：Welford 一遍求 (μ, σ²)，再从 DRAM 读第二遍归一化；多读一次 x，但寄存器压力很小（v4）

## 8. 踩坑记录

| 坑 | 后果 | 修正 |
|---|---|---|
| `row = threadIdx.x / 32` 漏了 blockIdx | 所有 block 都算第 0~3 行，其余行保持 NaN | `(blockIdx.x * blockDim.x + threadIdx.x) / 32` |
| `int VPT` 非 constexpr | `float buf[VPT]` 变长数组，设备代码编译不过 | `constexpr int VPT` |
| 用了不存在的 `n` | 编译错误 | 行长就是模板参数 `NCOL` |
| 写回用 `tid` 做下标 | 下标与读入时不一致 | 沿用 `i * 32 + lane` 和 `buf[i]` |
| `const float* x[r] = …` | 声明了名叫 x、长度 r 的数组，遮住参数 | `xr` / `yr` |
| `float s1 = 0.f; s2 = 0.f;` | 分号截断声明，s2 未声明 | 用逗号 |
| `+ gamma[j]` 写成平移项 | **编译通过、结果错**，只有 checker 能抓 | `+ beta[j]` |
| `.cu` 里 `N` 写死，`-DNCOLS` 不生效 | `make regs` 三次编出来都是 `<1024>`，误以为"都撑不住" | `#ifndef NCOLS … constexpr int N = NCOLS;` |
| 把 `0 bytes spill` 读成"撑不住" | 结论反了 | 0 spill = 全在寄存器里 = 撑得住 |

**习惯**：拿到结果先确认测的是不是自己以为的东西（看 kernel 名里的模板参数、程序打印的 `[M, N]`）。

## 10. 面试速答

- **单遍方差为什么不稳定？** 两个接近的大数相减，有效数字抵消；float 在 10⁶ 附近间隔 0.0625，在 10⁸ 附近间隔 8，算出的方差只能是间隔的整数倍。实测偏移 1000 误差 3.3，偏移 1e4 有 33.5% 的行出 NaN。
- **两遍法为什么不多花带宽？** 一行缓存在寄存器里，DRAM 只读一次写一次，"两遍"只在寄存器上走；多付的是一轮串行 all-reduce 和几十次乘加，memory bound 下被访存延迟盖住。
- **occupancy 越高越好吗？** 不是。要看在途字节数 = warp 数 × 每 warp 在途 load 数 × 每次字节数。v2 occupancy 从 78% 降到 61%，但 float4 让每次 load 搬 16 B，带宽反而最高；N = 4096 时 occupancy 只剩约 25%，靠每个 warp 的大量独立 load 仍跑满带宽。
- **spill 是什么？** 同时活着的值超过可用寄存器，编译器把一部分存到 local memory（物理上在 DRAM），用 STL/LDL 存取。寄存器上限 255/线程。
